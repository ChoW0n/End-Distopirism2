# 스프라이트와 이펙트 이미지 제작 능력 및 협업 기준

> 보관 메모 (2026-09-27): 이미지 생성 담당(gpt astra, Codex 에이전트)이 스스로 작성해 사용자가 전달한 문서를 원문 그대로 보관한다.
> 스펙이 아니라 참고 자료다. 이 리포가 따르는 결론은 SPEC-007 §9.3 에 적는다.

작성: 현재 대화의 Codex 에이전트
대상: 초원 및 다음 제작·검수·게임 구현을 맡는 에이전트
기준일: 2026-09-27 KST
목적: 작업 배분에 사용할 수 있도록 현재 도구의 기능, 실제 수행 결과, 실패, 미검증 영역을 구분한다.

## 1. 먼저 읽을 결론

나는 참조 이미지를 보고 새 래스터 이미지를 생성하거나 기존 이미지를 수정하도록 이미지 생성 도구에 요청할 수 있다. 실제로 이 대화에서 카일의 SD 캐릭터 시트와 수정본을 생성했다. 그러나 동일 캐릭터·무기·장착 구조를 여러 시점과 프레임에 정확히 유지하는 능력은 확보되지 않았다. 실제 검 착용 구조를 잘못 해석했고, 수정 결과에 오류가 남아 있는데도 해결했다고 보고했다.

따라서 현재 맡길 수 있는 역할은 참조 조사, 시안과 개별 포즈 후보 생성, 제한적인 이미지 수정 시도, 제작 규격 작성, 파일 검사와 검수 보조다. 반복 생성만으로 정확한 애니메이션 세트나 엔진 투입 가능한 에셋을 안정적으로 납품한다고 약속할 근거는 없다. 사용자가 승인한 그림이 생겨도 그 승인은 해당 그림과 용도에 한정한다.

이 문서는 능력 설명과 협업 계약이다. 새 스프라이트·이펙트 생성은 중단했으며, 이번 작성 중에는 기존 파일 조회와 비파괴 검사만 수행했다. 아래 제안 절차를 모두 이미 구현했거나 검증했다는 뜻은 아니다.

### 다음 에이전트가 즉시 알아야 할 사항

- 최신 카일 시트는 사용자 승인본이 아니다. 검 착용 수정이 반복된 작업본이다.
- 생성 도구의 호출 성공과 이미지의 구조적 정확성을 구분한다.
- 삼면도는 하나의 3D 물체를 자동 투영한 결과가 아니다. 각 그림 사이에 모순이 생길 수 있다.
- 수정 프롬프트에 보존 조건을 써도 다른 영역의 픽셀이 바뀔 수 있다.
- 투명 배경 요청 기능은 있지만, 결과의 알파와 가장자리를 별도로 검사해야 한다.
- 이펙트 한 장, 순서대로 놓은 시트, 실제로 자연스럽게 재생되는 이펙트는 검증 대상이 서로 다르다.
- Live2D 파츠처럼 보이는 이미지, PSD 파일, 실제 리깅된 모델은 각각 다른 납품물이다.
- 생성 성공률, 자동 검수 정확도, 일정·비용 절감률은 측정하지 않았다. 수치를 만들어 평가하지 않는다.

## 2. 근거를 읽는 방법

| 구분 | 의미 | 이 문서에서의 사용 |
|---|---|---|
| 직접 확인 | 현재 대화의 호출·결과 또는 이번 파일 검사에서 확인 | 카일 수정 실패, RGB 모드, 수정 영역 밖 픽셀 변화 |
| 도구 기능 확인 | 현재 노출된 입력·출력 기능에 존재 | 이미지 참조 전달, 투명 배경 요청, 로컬 파일 검사 |
| 과거 기록 | 제공된 대화 기록과 사용자 피드백에 존재 | 소각자 눈 색, 손 방향, 범고래 이펙트 관련 피드백 |
| 조건부 수행 | 데이터·규격·실행 환경이 갖춰지면 구현하거나 시도할 수 있음 | 피벗 정렬 코드, GIF 재생 확인, Unity용 메타데이터 작성 |
| 미검증 | 이번 증거로 품질·완료 여부를 입증하지 못함 | 연속 공격 모션의 안정적 양산, 네이티브 Live2D 납품 |

과거 기록에 성공이나 승인이 있어도 해당 원본, 프레임, 실제 재생 결과를 재검사하지 않은 항목은 직접 확인으로 올리지 않았다. 표의 배분 권고는 벤치마크 점수가 아니라 현재 증거에 따른 작업 판단이다.

## 3. 현재 사용할 수 있는 제작 수단

### 3.1 이미지 생성 도구

이 세션의 기본 래스터 생성·편집 경로는 내장 이미지 생성 도구다. 나는 참조 선택, 프롬프트 작성, 호출, 결과 확인을 수행한다. 생성기가 그림을 출력하며, 내가 결과의 모든 픽셀을 직접 제어하는 구조는 아니다.

현재 호출 인터페이스에서 직접 지정할 수 있는 항목은 다음과 같다.

| 항목 | 가능한 지정 | 실제 한계 |
|---|---|---|
| 프롬프트 | 대상, 포즈, 시점, 톤, 구도, 수정점, 보존 조건을 자연어로 전달 | 지시 준수와 기하학적 정합성 보장 없음 |
| 참조 이미지 | 로컬 이미지 경로들을 전달 | 참조마다 역할을 명시해도 특징 혼합·누락 가능 |
| 최근 대화 이미지 | 필요한 최근 이미지 수를 지정하는 경로 | 로컬 경로 방식과 함께 사용하지 않음. 현재 인터페이스에서는 최근 최대 5장 범위 |
| 투명 배경 | 투명 배경 요청 여부 | 요청값만으로 실제 알파 품질을 확정할 수 없음 |

현재 기본 호출에는 시드, 샘플링 스텝, CFG, 좌표 마스크, OpenPose, 깊이 지도, ControlNet, LoRA 학습, 정확한 출력 폭·높이, 프레임 시간, PSD 레이어 등의 전용 입력이 노출되어 있지 않다. 자연어로 비슷한 결과를 요청하는 것과 해당 기능을 실제로 제어하는 것은 다르다.

같은 프롬프트와 참조를 다시 넣어도 동일한 픽셀을 재현한다고 약속할 수 없다. 내부 이미지 모델의 버전·구조·학습 자료를 이 작업 결과만으로 특정하지 않는다. 대화 모델의 이름이 이미지 생성 모델의 이름을 증명하지도 않는다.

다른 이미지·영상 커넥터나 API 경로가 존재할 수 있지만 이 제작의 검증 결과에 포함하지 않는다. 외부 경로의 비용, 권한, 품질, 기능은 별도로 확인해야 하며 이번 문서를 근거로 임의 전환하지 않는다.

### 3.2 파일 분석과 코드 작업

파일 목록, 크기, 이미지 모드, 알파 범위, 해시, 픽셀 차이 등을 읽고 계산할 수 있다. 이번 문서에서도 Pillow와 NumPy를 이용해 기존 PNG를 검사했다. ZIP 목록 확인과 필요한 항목 추출, 프레임 메타데이터 작성, 이미지 조립용 코드 작성도 작업 조건이 갖춰지면 수행할 수 있다.

다만 코드 작성 가능성은 현재 프로젝트에서 구현·실행·승인됐다는 증거가 아니다. 현재 운영 규칙상 이미지 생성과 편집은 기본적으로 이미지 도구로 수행한다. 코드로 이미지 픽셀을 바꾸는 후처리를 실제 실행하려면 해당 요청의 범위와 허용된 작업 방식을 확인한다. 이 문서는 그러한 후처리를 실행하라는 추가 승인으로 해석하지 않는다.

### 3.3 참고 자료 조사

사용자가 제공한 이미지와 스프라이트를 열어 형태·색·자세를 비교할 수 있고, 필요하면 웹에서 실제 착용·동작 사진을 찾아볼 수 있다. 그러나 파일명이나 이미지 설명문만 읽은 것을 실제 이미지 검토로 보고해서는 안 된다. ZIP을 열었다고 내부의 모든 스프라이트와 GIF를 검토한 것도 아니다.

## 5. 스프라이트 제작의 구체적인 한계

### 5.1 화풍과 캐릭터 정체성

굵은 외곽선, 셀 셰이딩, 저채도 팔레트, 등신 등은 프롬프트와 참조로 유도할 수 있다. 그러나 특정 스프라이트팩과 선 굵기·음영 경계·눈 크기·해부학적 비율이 정확히 일치한다고 보장하지 못한다. 여러 캐릭터를 한꺼번에 생성하면 서로 비슷해지거나 각자의 톤이 달라질 수 있다.

SD는 머리만 키운 LD와 다르다. 짧아야 할 하체가 길어지는 문제, 긴 코트 때문에 몸통 길이를 잘못 읽는 문제, 전체 축소로는 해결되지 않는 관절 비율 문제를 따로 확인해야 한다. 정확한 등신은 머리와 신체 기준점을 정해 측정할 수 있으나, 머리카락 끝과 두개골 기준의 차이를 먼저 합의해야 한다.

눈 색을 바꾸는 요청에서도 눈동자 방향, 눈꺼풀, 하이라이트가 함께 바뀔 수 있다. 색상 지정만으로 정체성과 시선까지 보존되지 않는다. 과거 사용자 기록에도 소각자의 금안·적안, 사시처럼 보이는 눈, 일부 프레임의 수정 누락이 지적되어 있다. 그 기록을 이번에 전체 파일로 재검증한 것은 아니다.

### 5.2 손과 무기

가장 위험한 항목은 손의 해부학적 좌우, 엄지의 보이는 쪽, 손잡이의 통과 위치, 손목과 팔꿈치의 연결, 날이 향하는 방향이다. 멀리서 자연스러워 보이는 포즈에도 손잡이가 손바닥을 뚫거나 손가락이 무기를 감싸지 않는 문제가 생길 수 있다.

무기의 고정형 구조를 텍스트로 선언해도 길이·두께·코등이·날·손잡이·부품 수가 바뀔 수 있다. 무기가 프레임 안에 들어가도록 자동으로 눌리거나 짧아지는 결과도 검수 대상이다. 그립 상세도는 손과 손잡이 주변만 보여도 된다. 전체 무기는 별도 패널에서 확인한다.

### 5.3 시점과 장착

삼면도는 같은 무기의 실루엣을 복사해서 맞추는 작업이 아니다. 검과 검집의 넓은 면, 두께, 코등이 축, 몸에 매다는 지점, 앞뒤 기울기를 먼저 한 구조로 정의해야 한다. 그 구조를 각 시점에서 어떻게 보이게 할지 정해야 한다.

이번 카일의 수정에서는 이 순서를 지키지 않았다. 앞서 나는 정면에서 코등이 폭을 보이고 측면에서 좁혀야 한다고 설명했다. 사용자가 요구한 몸 옆에 납작하게 차는 배치에서는 반대였다. 이후에도 코등이를 가리는 식의 수정으로 원인을 해결했다고 보고했다. 이 잘못은 생성기 지시 불이행만의 문제가 아니라 내 해석·검수·보고의 실패다.

검 착용 방식에는 변형이 있으므로 모든 검이 반드시 한 방향으로만 착용된다고 일반화하지 않는다. 카일에 채택한 배치는 왼쪽 허벅지 바깥을 따라 검집의 넓은 면이 놓이고 손잡이가 앞, 끝이 뒤쪽 아래를 향하는 형태다. 이 배치의 정면·후면은 얇은 쪽을, 왼쪽 측면은 넓은 쪽을 주로 보게 된다.

### 5.4 연속 프레임

개별 이미지 생성은 뼈대와 물체 변환을 공유하는 애니메이션 시스템이 아니다. 프레임마다 손목 위치, 무기 길이, 중심, 얼굴, 의복의 접힘이 달라질 수 있다. 두 장을 순서대로 재생한다고 중간 동작이 자동으로 자연스러워지지 않는다.

이미지 사이의 이동·회전·확대·페이드로 움직임을 연출할 수는 있다. 그러나 그것은 실제 관절 동작이나 유체 변화가 새로 생성된 것과 다르다. 영상에서 프레임을 추출해도 캐릭터·무기 정합성이 자동 확보되는 것은 아니다.

공격에서 확인할 것은 준비 → 힘이 실리는 방향 → 접촉 → 회수의 연결이다. 단순한 좌우 반전은 장착한 허리, 주손, 비대칭 복장까지 바꾸므로 오른손 사용자 캐릭터의 반대 시점을 대체하지 못할 수 있다.

아래 항목은 시도 가능한 외형 범위다. 이 문서 작성 시 각 항목의 완성 팩을 새로 만들거나 엔진 재생으로 검증하지 않았다.

| 이펙트 종류 | 생성 요청으로 다룰 수 있는 요소 | 반드시 확인할 실패 |
|---|---|---|
| 참격·궤적 | 호, 길이, 두께, 날카로운 끝, 잔상 | 실제 무기 이동과 반대 방향, 타격부 불명확, 고정 피벗 없음 |

| 루프 효과 | 반복을 의도한 여러 단계 요청 | 마지막→처음 연결, 밝기·부피 점프, 반복 흔적 |

### 6.1 한 장과 애니메이션은 별도 납품이다

정지 그림이 역동적으로 보이는 것만으로 자연스러운 애니메이션이라고 부를 수 없다. 프레임별 표시 시간, 효과의 중심, 진행 방향, 발동 시점, 충돌 시점, 사라지는 단계가 필요하다. 프레임 수를 늘리는 것만으로 이 관계가 좋아지지 않는다.

### 6.2 투명도와 블렌딩

일반 알파 합성, 가산 합성, 곱하기 등 어떤 블렌딩을 쓸지 정해야 한다. 검정 배경의 섬광 이미지는 가산 합성에서 쓸 수 있지만 투명 PNG와 같은 납품물은 아니다. 검정 배경을 제거하는 과정에서 검은 연기나 어두운 윤곽이 같이 지워질 수 있다.

연기·발광·가느다란 불꽃처럼 반투명 픽셀이 많은 그림은 배경색 오염과 테두리 잔색이 특히 문제다. 원본이 배경과 이미 합성됐다면 정확한 원래 색과 알파를 한 장만으로 유일하게 복원할 수 없는 경우가 있다. 밝기로 알파를 만드는 방식은 색·소재에 따라 실패한다.

알파가 존재한다고 정상은 아니다. 가장자리의 밝은 테두리, 검은 테두리, 프리멀티플라이드 알파와 스트레이트 알파 설정 차이도 실제 합성에서 검사해야 한다. 생성 이미지만 보고 엔진 블렌딩까지 검증했다고 말할 수 없다.

### 6.3 게임에서의 타격감

카메라, 타격 정지, 피격 포즈, 음향, 번쩍임, 레이어 순서, 모션 속도와 효과 타이밍이 함께 작동한다. 나는 규격과 재생 코드를 작성하는 데 참여할 수 있지만, PNG 한 장으로 최종 타격감을 납품한 것은 아니다. 현재 프로젝트의 전투 규칙과 실제 재생을 확인해야 한다.

### 6.4 물리 데이터와 고급 텍스처

노멀맵·플로맵·깊이맵처럼 보이는 이미지를 그리게 요청할 수는 있다. 하지만 해당 채널이 올바른 좌표계·값 범위·시간 흐름을 가진 유효한 데이터라는 증거는 아니다. 수치적 정확성이 필요한 데이터는 명시적 계산·베이크·셰이더 테스트를 통해 검증한다. 이번 작업에서 그러한 데이터 제작은 입증하지 않았다.

## 7. 파츠 분할과 컷신에서 구분할 것

래스터 이미지에서 머리·눈·입·팔·무기 등을 나누는 작업에는 보이는 픽셀 추출과 가려진 부분을 새로 그리는 작업이 섞인다. 원본에 없는 겨드랑이, 코트 안쪽, 손 뒤의 손잡이는 단순 추출로 얻을 수 없다. 생성 복원 결과는 추정이며 별도 승인이 필요하다.

분리 파일이 있어도 관절을 움직일 때 틈이 벌어지거나 파츠 크기가 맞지 않을 수 있다. 원래 포즈로 다시 합성했을 때의 일치, 각 파츠의 기준 좌표, 겹침 여유, 회전 중심을 확인해야 한다. 검정 파츠를 검정 의상 위에서 찾는 경우 밝기만으로 위치를 검출하지 않는다. 좌표와 마스크를 명시하는 쪽이 재현 가능하다.

PNG 여러 장 또는 레이어가 든 PSD를 만들었다고 Live2D Cubism 모델 제작을 완료한 것은 아니다. 메시, 디포머, 파라미터, 물리 설정, 원본 프로젝트, 내보낸 모델, 실제 재생 검증이 각각 필요하다. 이번 증거로 네이티브 Live2D 모델 납품 능력을 확정할 수 없다.

| 시트 패킹 | 셀 좌표, 패딩, 회전 금지, 아틀라스 정보 | 개별 프레임의 그림 일관성 |
| 프레임 순서·시간 | 정한 순서와 표시 시간으로 재생 | 불연속 포즈 사이의 올바른 중간 동작 |
| 색 변환 | 마스크로 지정한 영역의 색 계산 | 눈·피부 등 영역을 항상 정확히 자동 식별 |
| 배경 제거 | 적합한 입력에서 단색 배경 분리 | 배경과 섞인 반투명 색의 완전 복원 |
| 부분 합성 | 지정 마스크 밖 원본 픽셀 보존 | 마스크 경계, 새 부분의 해부학적 정확성 |
| 파츠 조립 | 명시 좌표·회전 중심의 재현 | 가려진 신체·무기 면의 정확한 생성 |
| QA 스크립트 | 파일 존재, 모드, 크기, 해시, 누락 검사 | 미술 품질·공간 구조의 완전 자동 판정 |

정확한 피벗과 좌표를 JSON이나 CSV로 기록할 수 있다. 하지만 알파 범위의 최하단 픽셀을 무조건 발바닥으로 잡으면 검 끝이나 코트 자락을 발로 오인한다. 자동 추정과 사람이 승인한 기준점을 구분해야 한다.

## 11. 권장 협업 구조

| 담당 | 책임 | 다음 담당자에게 넘길 근거 |
|---|---|---|
| 초원 | 디자인·게임 규칙·최종 사용 승인 | 승인 이미지와 적용 범위 |
| 생성 담당인 나 | 참조 확인, 구조 해석, 후보 생성, 오류 기록 | 사용한 참조, 프롬프트, 결과, 잔여 문제 |
| 구조 검수 담당 | 인체·손·무기·착용·시점의 일관성 확인 | 실제 위치가 표시된 지적, 통과·실패 판정 |
| 파일 처리 담당 | 알파·패킹·크롭·피벗·좌표 관리 | 처리 코드, 설정, 변환 전후 결과 |
| 게임 구현 담당 | 재생·합성·타격 동기화·C# 연동 | 실제 엔진 캡처, 재생 영상, 실행 로그 |

다른 에이전트가 맡는다는 이유만으로 정확성이 보장되지는 않는다. 각 담당자는 자신의 통과 조건과 증거를 남긴다. 한 에이전트가 여러 역할을 수행하더라도 생성과 검수의 판정 근거는 분리한다.

### 작업 단위를 작게 잡는 기준

1. 대표 포즈 한 장에서 얼굴·비율·무기 구조를 먼저 승인한다.
2. 가장 어려운 손·그립·장착 각도를 시험한다. 쉬운 대기 포즈의 성공으로 어려운 공격을 통과 처리하지 않는다.
3. 승인된 포즈와 규격으로 다음 프레임을 만든다.
4. 공격·이펙트는 실제 순서와 시간으로 합성해 본다.
5. 전체 모션에서 동일성이 확인되면 팩으로 묶는다.

같은 구조 오류가 구체적인 수정 후에도 반복되면 실패 패턴을 기록하고 방법을 바꾼다. 반복 횟수 기준은 프로젝트 예산에 따라 정하되, 예를 들어 두 번의 교정 후에도 같은 오류가 남으면 더 작은 영역의 편집, 명시 마스크 합성, 검증된 리그·3D 블록아웃, 사람의 직접 수정을 검토한다. 이 예시는 측정된 최적 횟수가 아니다.

## 12. 요청 시 제공하면 좋은 입력

### 캐릭터와 무기

- 승인 원본 이미지와 버전. 최근 생성본과 승인본을 구분한다.
- 원작·톤·포즈·장착 구조 등 각 참조의 용도.
- 성별, 외모, 신체 비율, 눈 색, 고유색, 비대칭 특징.
- 해부학적 주손, 무기 휴대 위치, 칼날·코등이·손잡이 구조.
- 요청 포즈, 바라보는 방향, 카메라 높이, 실제 게임 표시 크기.
- 수정 가능한 부위와 비교할 기준점.

### 프레임과 이펙트

- 모션 이름, 프레임 수, 각 단계의 목적, 필요한 순서.
- 이펙트가 시작·접촉·종료하는 시점과 붙을 위치.
- 본체와 효과의 레이어 순서, 알파 방식, 블렌딩 방식.
- 각 효과의 용도와 방향. 이름만 바꾼 같은 효과의 반복은 피한다.
- 좌표계, 피벗, 바닥 기준, 엔진의 실제 표시 비율.

필수 값이 없으면 가정과 미확정 값을 명시한다. 파일명에 적힌 무기·동작을 눈으로 확인하기 전 확정하지 않는다. 셀 크기를 엄격하게 요구하는 작업이라면 생성 단계와 패킹 단계를 나누어 계약한다.

## 13. 검수와 승인 기준

### 13.1 스프라이트

- [ ] 승인 원본과 얼굴·눈 색·헤어·등신이 일치하는가.
- [ ] 손의 좌우, 엄지, 손목, 팔꿈치가 포즈에 맞는가.
- [ ] 손잡이를 실제로 감싸며 신체를 관통하지 않는가.
- [ ] 날·코등이·손잡이·검집의 구조와 개수가 유지되는가.
- [ ] 시점 변화에 따른 폭·두께·가림이 한 물체로 설명되는가.
- [ ] 장비가 허리·끈·손과 물리적으로 연결되어 있는가.
- [ ] 발 접지와 무게중심이 자연스러운가.
- [ ] 무기 끝·머리·발이 잘리지 않았는가.
- [ ] 수정 대상 밖의 얼굴·복장·무기 상세가 바뀌지 않았는가.

### 13.2 알파와 파일

- [ ] 파일을 실제로 열 수 있고 요구 포맷·크기인가.
- [ ] 투명 납품이면 알파 채널과 배경 알파 0이 존재하는가.
- [ ] 바깥 한 픽셀만 투명한 가짜 통과가 아닌가.
- [ ] 체크무늬·바닥 그림자·원하지 않은 배경이 픽셀로 남지 않았는가.
- [ ] 밝고 어두운 배경 양쪽에서 가장자리와 내부 구멍이 정상인가.
- [ ] 이미지별 피벗·크롭 원점·프레임 순서를 기록했는가.
- [ ] 패킹 과정에서 비대칭 캐릭터가 임의 회전·반전되지 않았는가.

### 13.3 연속 동작과 이펙트

- [ ] 실제 표시 시간으로 재생했는가.
- [ ] 준비·타격·회수의 방향이 이어지는가.
- [ ] 손과 무기 접점, 길이, 날 방향이 프레임마다 유지되는가.
- [ ] 이펙트 원점과 타격 위치가 맞는가.
- [ ] 증식·소멸·잔상이 갑자기 끊기거나 튀지 않는가.
- [ ] 루프가 필요하면 마지막과 첫 프레임 연결을 확인했는가.
- [ ] 실제 블렌딩·레이어·카메라에서 확인했는가.
- [ ] 캐릭터와 전투 정보의 가독성을 해치지 않는가.

체크리스트를 작성한 것과 통과한 것은 다르다. 검사하지 않은 항목은 미검증으로 표시한다. 시각 검사만으로 정확한 픽셀·시간·엔진 동작을 확인했다고 기록하지 않는다.

## 16. 이 프로젝트에 유지할 지시

- 초원은 원작·스프라이트팩의 톤을 실제로 확인해 반영할 것을 요구했다.
- SD와 LD를 따로 제작하고, SD의 하반신이 지나치게 길어지지 않게 해야 한다.
- 카일은 이상을 연상시키는 내향적이고 가는 인상을 원했으며 근육질 메인 캐릭터를 원하지 않았다.
- 확정하지 않은 와이어·가변형 무기·기계 장치를 임의로 추가하면 안 된다.
- 시트의 여백은 동일성 유지에 필요한 정면·측면·후면, 얼굴, 장비 구조, 그립 등으로 사용한다.
- 그립 상세에는 손잡이를 쥔 부분만 들어가도 된다. 전체 무기를 그 칸에 넣으려고 변형하면 안 된다.
- 본체와 효과는 최신 요청에 맞춰 분리한다. 과거 문서의 궤적 포함 예외를 최신 지시보다 앞세우지 않는다.
- 문서마다 프레임 수·생성 단위가 다를 수 있다. 현재 대상 작업의 최신 사용자 지시를 확인한다.
- 과거 생성본을 새 스타일 기준으로 자동 채택하지 않는다. 수정 대상 이미지와 스타일 참조를 구분한다.
- 지금은 사용자가 이미지 작업 중단을 요청한 상태다. 이 문서 전달을 새 이미지 생성 재개로 해석하지 않는다.

## 18. 최종 작업 배분 판단

참조를 이용한 후보 제작과 구체적인 실패 분석에는 사용할 수 있다. 정확한 구조와 시간적 연속성이 필요한 최종 에셋은 별도 검증과 필요시 직접 수정이 필요하다.

생성 횟수를 늘리는 것보다 승인본을 유지하고, 바뀐 부분을 비교하고, 실제 재생에서 통과한 근거를 남기는 역할을 중심으로 협업한다. 현재 카일 작업은 그 기준에서 승인 전 상태이며, 이 문서가 전달됐다는 이유로 완료 처리하지 않는다.
